## 一、改造背景

调研报告指出当前 AI 对话执行链路的四个结构性短板：

1. **一块大知识 + 全量目录**：`OpsToolRegistry.SYSTEM_KNOWLEDGE`（93 行整块业务知识）与 33 个工具的全量参数目录每轮全量注入 Prompt，token 成本随工具数线性增长，且无关工具干扰判定聚焦度；
2. **校验只查"形"不查"义"**：必填/枚举/类型校验通过后，"项目名写错""同名歧义""写入目标不存在"等"看起来对但其实错"的参数会直接流入执行器；
3. **记忆硬截断**：`CONTEXT_MESSAGES = 6` 导致长会话丢失关键约束（如"这个任务是给三一重能的"），且无跨会话记忆；
4. **无回归尺子**：Prompt 与判定规则改动无基线保护，无法量化验证不劣化。

本次落地即为上述四项（P0-1 / P0-4 / P0-3 / P0-2），全部为**纯后端改造，不引入新依赖**。

## 三、P0-1 技能卡拆分与渐进披露

### 3.1 设计

对齐 Anthropic Agent Skills 的渐进披露（Progressive Disclosure）模式，将原「一块大知识 + 全量目录」改为三层结构：

| 层 | 注入内容 | 注入时机 | 体量 |
| --- | --- | --- | --- |
| 第一层（常驻） | `GLOBAL_RULES`（红线约束）+ `briefCatalog()`（13 行目录：版块名 + 一句话能力 + 该版块工具名清单） | 每轮必注入 | 约 400 tokens |
| 第二层（按需） | 命中版块的 `knowledge()`（完整业务口径） | 本轮消息命中该版块触发词后注入 | 约 100 字符/版块 |
| 第三层（按需） | `registry.catalog(module)`（命中版块的工具参数详情） | 同上 | 约 400~600 字符/版块 |

关键实现（[OpsSkillCards.java](file:///d:/2、开发源码/基于AI的部门工作管理软件0812/backend/src/main/java/com/dept/mgmt/aiworkspace/ops/OpsSkillCards.java)）：

- 13 张技能卡以 `record OpsSkillCard(code, name, summary, triggers, knowledge)` 静态定义，`code` 与 `OpsToolRegistry` 工具注册的 module 名严格一致；
- `match(content)`：触发词正则预筛（本地零成本，懒编译一次），返回本轮命中的 0..n 张卡；
- `briefCatalog()`：由 `registry.all()` 按版块分组生成目录，工具名自解释（`版块.动作`），不含参数；
- [OpsToolRegistry.java](file:///d:/2、开发源码/基于AI的部门工作管理软件0812/backend/src/main/java/com/dept/mgmt/aiworkspace/ops/OpsToolRegistry.java) 删除 93 行 `SYSTEM_KNOWLEDGE` 常量，`catalog()` 委托新增的 `catalog(String module)` 重载按版块过滤。

### 3.2 与调研报告方案的差异：单轮渐进（有意决策）

调研报告 P0-1 原方案为"两段式"（首轮选版块 → 次轮加载详情），会**增加 1 次模型调用/轮**。在 35 次/分钟限流硬约束下，本次采用**单轮渐进**：触发词规则命中版块后，当轮 Prompt 即同时携带目录 + 命中版块详情；规则未命中时仅给目录兜底，模型仍可凭自解释工具名选对工具，缺参由后端声明式追问补齐。

**效果**：LLM 调用次数保持 1 次/轮不变；按字符口径估算，decide 的常驻知识注入量由约 1 万字符量级（93 行整块知识 + 33 工具全量参数）降至单版块命中约 1.5K、未命中约 0.8K，**降幅约 80%~90%，远超验收线 ≥50%**（精确数值可由后续统计脚本复核；golden set 已用 prompt 断言锁结构，见 6.3）。

### 3.3 未新增常驻模型调用

- 渐进披露：纯本地正则预筛，0 次额外调用；
- 滚动摘要（P0-3）：仅当未摘要消息超过阈值才触发 1 次摘要调用（均摊约 +0.25 次/轮），失败自动降级、不重试（见第五节）。

## 四、P0-4 参数语义校验

### 4.1 设计

现有校验只查必填/枚举/类型（"形"）。本次在 `validate → semanticValidate → checkPerm` 链路中新增语义层（[SystemOpsService.java](file:///d:/2、开发源码/基于AI的部门工作管理软件0812/backend/src/main/java/com/dept/mgmt/aiworkspace/ops/SystemOpsService.java)），补三类"义"的洞：

**① 实体存在性与歧义检测**（`OpsParam.resolve` 标注 + `EntityMatch`）

- `OpsParam` 新增 `resolve` 字段（`"project"` / `"user"`），共 14 处标注（task.create / project.detail / contract.bindProject / design.schemeList / production.woList / production.kitting / delivery.shipmentList / delivery.progress / delivery.acceptanceList / ecn.list / cost.ledger / cost.settle / aftermarket.repairList / aftermarket.repairCreate 的 projectName，以及 task.create / task.list 的 assignee）；
- `OpsToolRegistry` 新增 `record EntityMatch<T>(T entity, List<String> candidates)` 与 `none() / ambiguous() / unique()` 静态工厂，及不抛异常的 `matchProject / matchAssignee`（原 `resolveProject / resolveAssignee` 改为基于 match 的封装，异常文案保持不变）；
- 语义行为：
  - **未找到** → 追问引导：`未找到项目「X」，请确认项目名称（可先说「查一下项目」核对）`；
  - **歧义（多条命中）** → 返回编号候选列表（上限 5 条）强制追问，**禁止默认取第一条**；
  - **唯一命中** → 参数自动规范化为库内标准名（如"三一重能" → "三一重能一期"，"1"/"2" 亦可按项目 ID 解析），写入类后续确认卡片展示标准名，杜绝"错名落库"；
- **只读宽松、写入严格**（调研报告 P0-4 风险条款）：`task.list.projectName`、`project.list.name`、`archive.list.projectName` 有意不标注 resolve，保持关键词查询行为，避免追问过度伤害体验。

**② 写入前置校验**（`OpsTool.precheck`）

- `OpsTool` 新增 `precheck`（`BiFunction<Map<String,Object>, LoginUser, String>`，null = 通过）；
- 3 个写入工具挂接：
  - `task.changeStatus` / `task.addWorkHour`：任务不存在 → `任务 X 不存在，请先查询任务列表核对任务ID`；
  - `contract.bindProject`：合同不存在或不可访问 → `合同 X 不存在或不可访问，请先查询合同核对ID`；
- precheck 在确认流之前拦截，避免"确认后才报错"的糟糕体验。

### 4.2 校验链路（改造后）

```
tryOps → decide（LLM 判定，JSON 契约）
       → handleTool:
           validate（必填/枚举/类型——原有）
           → semanticValidate（实体解析/歧义/前置——新增）
           → checkPerm（角色/精细权限——原有）
           → 只读工具直接执行 / 写入工具进 pendingStore 二次确认（原有确认制不变）
```

### 5.2 滚动摘要（[AiMemoryService.java](file:///d:/2、开发源码/基于AI的部门工作管理软件0812/backend/src/main/java/com/dept/mgmt/aiworkspace/service/AiMemoryService.java)）

| 参数 | 值 | 说明 |
| --- | --- | --- |
| `UNSUMMARIZED_THRESHOLD` | 12 | 未摘要消息超过 12 条才触发（均摊每 4 条新消息 1 次摘要调用） |
| `KEEP_RECENT` | 8 | 摘要只压缩第 8 条之前的消息，近期消息仍原文携带（保留原文，摘要只作辅助——调研报告风险条款） |
| `SUMMARY_FALLBACK_MAX` | 2000 | 摘要失败时降级为原文拼接截断 2000 字符 |
| `MAX_FACTS` | 3 | 每次摘要最多沉淀 3 条稳定事实 |
| `RECALL_LIMIT` | 5 | 每轮注入最近 5 条长期记忆 |

- 摘要调用复用既有网关能力点 `CAP_DOC_SUMMARY`，以 JSON Schema 约束输出 `{summary, facts}`；`extractJson` 容错围栏解析；
- **全程 try-catch**：摘要/落库任何失败均静默降级，**绝不阻塞对话主流程**；
- 摘要成功后更新 `ai_conversation.summary / summary_msg_id` 水位线。

### 5.3 注入点

| 场景 | 注入内容 |
| --- | --- |
| `SystemOpsService.decide()`（工具判定） | 【会话此前摘要】+【用户长期记忆】（最近 5 条） |
| `AiChatService.generalChat()`（通用对话） | 同上，插入在【对话历史】之前 |

### 5.4 长期记忆防污染（mem0 教训落地）

- `user_id` **严格隔离**检索（`recall(userId)` 按当前登录用户过滤）；
- 只在摘要链路中由 LLM 抽取"稳定事实"（带 `conversation_id` 溯源），与既有记忆去重后写入，`confidence=0.8`；
- 逻辑删除（`deleted`）兜底，可人工清理。

### 6.2 测试脚手架（[OpsTestHarness.java](file:///d:/2、开发源码/基于AI的部门工作管理软件0812/backend/src/test/java/com/dept/mgmt/aiworkspace/ops/OpsTestHarness.java)）

- **纯 JUnit5 + Mockito，不起 Spring 上下文**：17 个依赖 mock + 真实 `OpsToolRegistry / OpsSkillCards / OpsPendingStore / SystemOpsService`；
- **MyBatis-Plus lambda 缓存**：单测环境无 MyBatis 启动，静态块 `TableInfoHelper.initTableInfo(new MapperBuilderAssistant(new MybatisConfiguration(), ""), ...)` 注册 Project/SysUser 列缓存，否则 `like` 条件抛 `can not find lambda cache`；
- **模拟 SQL like**：`selectList(any())` 用 Answer 实现 `filterByWrapperParams`——因 MP wrapper 的 `like` 参数**惰性注册**，需先反射 invoke `getSqlSegment()` 物化参数再过滤（无参数 = 全量兜底），从而让"按项目名 like 过滤"在 mock 层真实生效；
- 网关应答链：`thenReturn(r1, r2, ...)` 按 `[decision, decisionRetry, followup.decision]` 顺序消费；`SecurityContextHolder` 注入 `LoginUser(1L, "tester", role, List.of())`。

### 6.3 基线意义

- **先有尺子**：63 用例全部通过即当前基线（本次为首个基线版本），此后任何 Prompt / 判定规则 / 校验链路改动必须 `mvn test` 过基线才可合入；
- Prompt 结构由 `promptContains / promptNotContains` 直接锁定（例：生产管理用例断言 prompt 含【命中版块：生产管理】与"开工卡点"，**不含**合同管理口径"联系方式为敏感字段"——即渐进披露的"只注入命中版块"被用例化）；
- 语义校验专项用例共 **25 条**（golden set 17 + 判定逻辑单测 8），其中错名/同名/缺前置阻断类 16 条、参数规范化类 9 条，**全部断言追问/拦截而非误执行**，满足调研报告"构造 20 条错名/同名/缺前置用例全走追问"的验收要求。
